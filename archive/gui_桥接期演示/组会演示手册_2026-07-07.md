# 组会演示手册:GBPlanner-in-world-model 桥接式融合

---

## 0. 口径声明(演示开场先念,一字不改)

> **本演示是「阶段性可视化演示」,不宣称这是稳定的最终版本。**
> 我们展示的是:主链已打通并全程有证据文件的桥接式融合——ROS1 原版 GBPlanner 通过自写薄桥接入 ROS2 world-model,形成 3D 数据链、规划链、控制消费链、去混流运动归因、gate 通过与公平对比。**这不是 ROS2 原生移植**(联网复核:官方无 ROS2 版 GBPlanner)。

三条纪律(遇到追问时兜底):

1. **live run 失败 ≠ 演示失败**。探索指标存在 run 间波动(与 frontier_lite 基线同性质),这正是我们做 N 次批跑统计的原因。live 挂了就按第 5 节 Fallback 清单打开存档证据,结论不变。
2. **不宣称的东西**:不说"稳定全绿"(全绿率见批跑统计);不说"完整 z 方向飞行闭环"(z 由飞控高度环保持,已证明的是低速 XY/Yaw 控制链 + 3D 输入行为对照);不说"3D 障碍物级对照"(5b 是传感 FOV 对照)。
3. **RViz 里颜色不作证据**,一切以 topic 名 + 消息类型 + 发布者为准(见第 2 节图例表)。

## 1. GUI 1:world-model / Gazebo 主仿真(平台本体)

### 启动

```bash
bash runbooks/world-model-jazzy/gui_demo_master.sh
```

(脚本由主线提供,负责拉起 world-model jazzy 仿真栈 + Gazebo GUI。启动后等飞机出现并起飞。)

### 讲解词(按顺序念)

1. **"这是 world-model,一个 ROS2 jazzy 无人机仿真平台,大家看到的是 Gazebo 主仿真窗口。"**
2. **飞机真实起飞**:"起飞是 SIM 真实物理,不是瞬移——我们有飞控黑匣子(BIN 日志)铁证:SIM 高度 +0.720m、电机输出 1950。此前为了让它真飞起来,修了 B1~B16 一整条真 bug 链,零 hack。"
3. **FCU = ArduPilot SITL**:"飞控是真实的 ArduPilot SITL,不是玩具控制器。所有控制命令最终都要过飞控这一关,这也是后面'消费直证'的意义——GBPlanner 的命令真的被飞控吃进去了。"
4. **odom = 2D SLAM**:"里程计来自机载 2D SLAM(X2)。平台原生是 2D 雷达,这是三大鸿沟之一;我们的 3D 输入是净增量加的 lidar3d 传感器,SLAM 链零触碰。"
5. **gate = 平台自动验收**:"平台自带 exploration gate 自动验收:accepted_goals≥3 且 path≥0.35m 才算达标,全部探针通过才算全绿(TASK_STATUS_OK)。后面所有成功率数字都是这个 gate 说了算,不是我们自己给自己打分。"

## 2. GUI 2:GBPlanner / RViz(规划器侧)

### 启动

```bash
bash runbooks/world-model-jazzy/gui2_rviz.sh
```

(脚本由主线提供,拉起 GBPlanner ROS1 侧 RViz。)

### RViz 对象图例表(核心——逐条对着屏幕指认;**颜色可配置,不作证据**,认 topic/类型/发布者)

| 对象 | topic | 消息类型 | 发布者 | 语义 |
|---|---|---|---|---|
| 点云(传感) | `/wm/points` | `sensor_msgs/PointCloud2` | 薄桥(world-model 3D lidar 过桥) | GBPlanner 的 3D 输入,来自 ROS2 侧 lidar3d,经自写 TCP 薄桥进 ROS1 |
| 点云(地图) | `/gbplanner_node/tsdf_pointcloud` | `sensor_msgs/PointCloud2` | voxblox | 3D TSDF 体素地图(GBPlanner 用它做体积增益规划) |
| 执行轨迹 | `/rmf_obelix/command/trajectory` | `trajectory_msgs/MultiDOFJointTrajectory` | `pci_general_ros_node`(PCI) | **唯一控制链输入,桥只接它**,这才是飞机真正要执行的轨迹 |
| 候选路径/图 | `/vis/*`(best_planning_paths、ref_path、RRG markers) | `visualization_msgs/Marker` / `MarkerArray` | `gbplanner_node` | **仅可视化,不进控制链**。接错这路 = 追一条没被选中的路 |
| ROS2 侧回流 | `/gbp/trajectory` | `trajectory_msgs/MultiDOFJointTrajectory` | 薄桥 ROS2 侧 | PCI 执行轨迹过桥回到 ROS2,交给 trajectory_to_intent 适配器消费 |

### 讲解词

1. **"传感点云(/wm/points)是 world-model 那边的 3D lidar 数据,经我们自写 TCP 薄桥过来的——官方 ros1_bridge 和 zenoh 双桥都实验判死了,这座桥是这个项目的第一块基石。"**
2. **"voxblox 用它建 3D TSDF 体素地图(/gbplanner_node/tsdf_pointcloud),史诗同框那次实测 9 万+ 体素点、z 跨度 13.2 米——2D 平台上长出了真 3D 地图。"**
3. **"重点看粉线纪律:RViz 里花花绿绿的路径大多是 /vis/* 可视化候选(绿线=planner 候选路径),不进控制链。真正执行的只有一条:/rmf_obelix/command/trajectory,发布者是 PCI,我们的桥只接它。接错就是追一条没被选中的路——颜色可以改配置,所以我们从不拿颜色当证据,只认 topic 和发布者。"**
4. **"这条执行轨迹回流到 ROS2 侧变成 /gbp/trajectory,由 fail-closed 的适配器转成飞控 intent——默认禁用、可一票 kill、限速、超龄轨迹丢弃、坐标 Procrustes 在线对齐。"**

### 讲解顺序(四步,严格按此顺序)

**第 1 步:公平对比 50% vs 0%(最硬的数字,先亮)**

> "同一套 EKF 修复、同环境、同 26 秒窗口口径下各跑 6 次:GBPlanner 桥接 gate 达标 **3/6 = 50%**,frontier_lite 基线 **0/6 = 0%**。基线的 accepted_goals 六次全等于 2,零方差——这是启动耗时蚕食窗口的结构性失败,不是随机;修复前基线曾有的 2/6 全绿被证实是 EKF 跑飞的'馈赠'。而且我们这边的 accepted 是真实运动到达(预到达剔除),口径比基线的纯时间计数更严。**公平口径下 GBPlanner 显著优于基线。**"

**第 2 步:final2 全绿 run(单 run 最佳证物)**

> "这是一次完整全绿 run(final2,run `20260707T111217`):TASK_STATUS_OK,gate accepted_goals=5、path=1.33m,适配器 GATE OK 闩锁 wp_done=5 全部为运动到达,strategy=gbplanner。全链条无任何探针失败。"

**第 3 步:5b 3D 行为对照(证明 3D 输入真的在起作用)**

> "同参数只改 3D 雷达垂直 FOV(±30°→±5°):输入点云 z 跨度 9.08m→0.48m(压扁 19 倍),voxblox 建图点数 121,479→54,129(近半),trajectory 的 z 机动收缩一个量级、从 1 条变 6 条频繁重规划,gate 结果随之改变——**GBPlanner 的行为确实受 3D 输入影响**。注意口径:这是传感 FOV 对照,不是障碍物对照。"

**第 4 步:修复链(顺手治好了上游平台)**

> "一路上我们根治了 world-model 上游的 EKF 参考系真 bug(罗盘 yaw 与 SLAM 位置参考系差 δ,一运动就发散跑飞 34m,BIN 验尸定案,修复 3 件套已入 clean 分支 99bcfa1),外加起飞链 B1~B16 修复,净 diff 零 hack。基线 path 方差极大(跨 3.4m)的根因就是这个 bug——修好之后大家才在同一起跑线上比。"

## 6. 提问预案(3 条,照念)

**Q1:为什么不把 GBPlanner 移植成 ROS2 原生,而要搭桥?**

> "我们 2026-07-07 联网复核过:官方 ntnu-arl/gbplanner_ros 的 16 个分支全是 ROS1,0 个 tag/release,没有任何官方 ROS2 移植。原版 GBPlanner + voxblox 是深度耦合的 catkin 栈,重写移植的工程量和引入新 bug 的风险都远超薄桥,而且移植后就不再是'冠军队原版算法'——桥接保住了算法本体的可信度。官方 ros1_bridge(jazzy→foxy RMW 层 bad_alloc)和 zenoh 双桥(header mismatch)都实验判死了,自写薄桥是实测下来唯一走通的路。"

**Q2:3D 到底证明了什么?**

> "准确口径:证明了 **GBPlanner 的感知、建图、规划行为确实受 3D 输入影响**——5b 对照里把垂直 FOV 压扁 19 倍,建图点数近半、轨迹 z 机动收缩一个量级、重规划模式和 gate 结果都变了。**但没有证明 z 方向飞行动作闭环**:飞机的高度目前由飞控高度环保持,已打通的控制链是低速 XY/Yaw。3D 体现在'脑子'(感知/建图/规划),还没有体现在'z 向动作'。"

**Q3:成功率 50% 这个数字怎么读?**

> "读法是**相对值,不是绝对值**:同一公平口径下基线是 0%(而且是结构性的 0——accepted 恒等于 2,零方差),GBPlanner 首批 6 run 达标 50%。后续 v2 批跑有波动(合并 12 run 达标 33%),但任何一批都显著优于基线的 0%,主结论'GBPlanner 显著优于 frontier_lite'不变。同时我们不宣称'稳定全绿'——全绿率仍受探索质量波动(A类)和与 GBPlanner 无关的探针波动(B类)影响,这是当前的诚实边界,也是下一阶段的改进方向。"
