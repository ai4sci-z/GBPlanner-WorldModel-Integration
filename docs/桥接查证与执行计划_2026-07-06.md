## 二、两个待定选型(需要用户拍板)

### 选型 A:3D 点云怎么来(Codex 风险A,正式对比的硬前提)
| 方案 | 内容 | 工作量/风险 |
|---|---|---|
| A1(推荐,分两步) | **先 2D→PointCloud2 转换节点做冒烟**(只验证桥路通,明确标注非真3D)→ **再给 navlab_iq_quad 的 SDF 加 3D gpu_lidar**(vertical samples 16~32、±15°,ros_gz_bridge 出 PointCloud2)做正式对比 | 冒烟=1个小节点;3D lidar=改 SDF+bridge 配置+新话题,中等;正统、可进 PR |
| A2 | 直接上 3D lidar,不做冒烟 | 一步到位但桥/适配器的坑会和传感器坑搅在一起,违背"每次只动一个变量" |

### 选型 B:ROS1(Noetic)↔ROS2(jazzy) 桥选型(Codex 清单#4)
| 方案 | 内容 | 风险 |
|---|---|---|
| B1(先试,推荐) | 官方 `ros:foxy-ros1-bridge` 现成镜像(20.04,内含 Noetic+Foxy+bridge),host 网络。ROS1 侧连 gbplanner-ref 的 master;ROS2 侧(Foxy)与 jazzy 栈靠 **DDS 跨版本互通**(标准消息 Odometry/PointCloud2/MultiDOFJointTrajectory 定义稳定;jazzy 对无 type-hash 端只 WARN——B16 已实测 micro-ROS agent 无 hash 也通) | Foxy↔jazzy 互通需实验验证;失败则转 B2 |
| B2 | zenoh-bridge-ros1(ROS1↔zenoh↔ROS2 jazzy 原生) | 引入新组件,但版本无关,是 ROS 社区对 jazzy 时代 ROS1 桥的主流答案 |
| B3 | 源码编 ros1_bridge(humble 容器+Noetic from source) | 工作量大,不推荐 |

## 三、分阶段执行计划(采纳 Codex 阶段0-5,含验收)

- **阶段 0 ✅ 已完成**:frontier_lite 全绿(run `20260706T130626`)+ 基线定档(批跑进行中,结果写入本目录)。
