### 3.3 `worldmodel理解_2_ROS图与数据流.md`

这份文档很重要，但有一个关键点要提醒：

它明确指出 world-model 当前并非标准 `map -> odom -> base_link` 链，而是 Cartographer 直接给 `map -> base_link`，`odom` 在很多地方只是 legacy 名字。

这会影响 ROS2 GBPlanner 迁移，因为很多 ROS2/导航代码默认会找：

```text
map -> odom -> base_link
```

但这个项目可能实际只有：

```text
map -> base_link
```

建议下一窗口把这一点作为 M1/M2 前置检查：

```text
不要默认存在 map->odom；
GBPlanner ROS2 的 world_frame / robot_frame / TF lookup 必须按 world-model 实际 TF 设计。
```

### 3.4 `worldmodel理解_3_探索策略接口_GBPlanner接入点.md`

这份文档直接给出了 ROS2 GBPlanner 接入点，价值很高：

- `strategy=external` 是让位机制；
- 外部 planner 必须发 `/navlab/fcu/setpoint/intent`；

- `trajectory_to_intent_stage4.py` 可继续作为第一版执行适配器；

## 4. stage6 半截工作审查

### 4.1 stage6_probefix5

`stage6_probefix5_apply.sh` 做的是：

- 修 `ros_probe.py.tmpl`；
- 对 publisher info discovery 增加重试；
- 如果 `/tf_static` 查不到 publisher info，则默认用 TRANSIENT_LOCAL QoS；
- 目标是避免 late joiner 错过 latched `/tf_static`。

这是合理修复，方向正确。

### 4.2 stage6_probefix6

`stage6_probefix6_apply.sh` 试图把 frame_contract 的 FCU pose 采样从：

```text
/ap/v1/pose/filtered
```

改为：

```text
/navlab/fcu/local_position_pose
```

理由是 `/ap/v1/pose/filtered` 是 micro-ROS DDS debug stream，匹配尾巴不稳定；而 `/navlab/fcu/local_position_pose` 是系统真实消费链路中的 MAVLink 回发位置，更适合作为 frame_contract 的 FCU pose 检查。

这个方向也合理。

但接力棒明确写了一个半截点：

```text
stage6 修复 ⑤半成品：
只改了 helpers/runtime_specs.go L459，
但渲染链没有生效。
实际赋值链是 runtime_artifacts.go L722
spec.FCUPoseTopic = frame.FCUPoseTopic
而 config/defaults.go 多处 default 仍是 "/ap/v1/pose/filtered"。
下一步要改 config/defaults.go 里的 frame_contract default + 测试同步 + 复跑验证。
```

这是下一个窗口必须优先处理的半截活。

### 4.3 stage6 结论

stage6 当前不应被视为完成。准确状态：

```text
probe 修复 ⑤/⑥方向正确；
⑤已相对完整；
⑥有半截修改，尚未验证渲染生效；
```
