# M5-c 长程 cohort 证据（2026-08-24）

## 结论

M5 仍为进行中，不能宣布完成。

- external GBPlanner 在最终高度口径下取得 2/2 独立 PASS，但只有 2 个完全同 SHA
  样本，不足以构成冻结的 6-run 算法比较。
- current-then WorldModel `6e48597` 的 `frontier_lite` 6-run cohort 为 4 PASS / 2
  FAIL。一次失败是跑飞后返航超时，一次是 workflow 成功未闩锁导致 runner
  `mission_wait` 超时。
- `dc41bc3` 修复了后一个 lifecycle bug；修复后两个 canary 为 1 PASS / 1
  真实返航失败。它们不并入 `6e48597` cohort。
- 两种策略的 `accepted_goals` 语义不同：GBPlanner 只计实际 waypoint 到达，
  `frontier_lite` 按时间段递增。因此只能比较各自 gate 通过率和安全收尾，不能把
  `accepted_goals=3` 当作同质算法质量指标。
- 所有 landing PASS 的 `descent_profile.ok` 仍为 false。WorldModel 当前对 AP LAND
  策略明确采用“下降曲线只审计、不阻断”，并非字段意外漏接；但这也意味着现有 PASS
  只证明 LAND handoff、touchdown、disarm 与 motors-safe，不能据此宣称下降率安全已验证。

## Lifecycle 修复 canary

`093206` 的根因是内建 workflow 首次 `ok=true` 后未闩锁；FCU 开始返航时 controller
ready 变 false，workflow 撤销完成状态并一直活到 runner deadline。WorldModel
`dc41bc3` 冻结首次成功 status，使有限 service 在 5 秒 hold 后自然退出。

| run | status | path m | 结果 |
|---|---|---:|---|
| `094244` | FAIL | 4.4088 | 真实 return timeout，距 home 2.9290 m；未 LAND |
| `094725` | PASS | 0.4407 | landing complete，约 106 s 结案，未触发 178 s mission_wait |

这证明 lifecycle 竞争已修复，但不修复 `frontier_lite` 偶发跑飞和返航失败。

## 高度源与 fail-closed

`/navlab/fcu/local_position_pose` 的发布者是 WorldModel
`navlab.real.companion.nodes.external_nav.MavlinkExternalNavSender`。它直接消费 FCU
`LOCAL_POSITION_NED`，再用 `z_up=max(0,-z_down)` 发布。因此 `25.621 m` 是 FCU
回传链上的值，不是 GBPlanner relay 自造；当前证据仍不能区分真实爬升与 EKF 发散。

GBPlanner `32f269f` 已将 planning z 限为 `(0.05, 3.0] m`，异常样本立即清除缓存，
并分别记录 `low_fcu_height`、`overheight_fcu_height`、`nonfinite_fcu_height`。只有后两类
使验收失败；起飞前和落地后的正常低高度保留为诊断计数。
