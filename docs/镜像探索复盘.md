# 镜像探索复盘(为什么花了时间,学到什么)

> 给组会"讲这个方向的探索"用。最后更新 2026-06-30。

## 1. Docker 镜像是什么
**镜像 = 把程序 + 它需要的整套运行环境(系统库/依赖/配置)打包成的"密封集装箱"。** 镜像=模板,容器=跑起来的实例。
- 用途:**可复现**(任何装了 Docker 的机器跑同一镜像,行为一致)+ **隔离**(不污染本机)。
- world-model 把整套仿真栈(ROS2+Gazebo+ArduPilot+SLAM)切成 **9 个镜像**,理想是"一条命令跑起来"。

## 2. 为什么对本任务"非必需"(关键)
问题**不在镜像本身**(它正是 world-model 的运行方式),在于:
1. **正常是"拉"现成镜像**(作者在自己机器/CI 构建好、推仓库,大家 `docker pull`)。**但本项目没公开镜像仓库**,我们只能**从源码现编**。
2. **从源码现编 = 把"为特定 Linux(Ubuntu24.04/CI)写死的栈"搬到本机,处处撞版本墙**(编译器、Python3.10 vs 3.11、Gazebo 版本、Fast-CDR…)——耗时就在这。
3. **更重要:跑通整个平台不是本任务核心。** mentor md 的核心是**算法理解 + 集成方案**。我们靠**读源码**就证明了 frontier_lite 是脚本占位、想清了集成机制、还**真跑出了 GBPlanner 核心决策**——这些**都不需要整个平台跑起来**。

## 3. 关于 MacBook(辨析:换 Mac 不会更好)
- **镜像里跑的永远是 Linux**:Windows 靠 WSL2、Mac 靠 Docker Desktop(都是 Linux 虚拟机),撞的是**同样的版本墙**(那是镜像内发行版的问题,和宿主 OS 无关)。
- 唯一和宿主有关的是 **CPU 架构**:**Apple 芯片(M1/2/3)是 ARM**,这些镜像多是 x86_64 → 在 Mac 上要**模拟(更慢)或重编 ARM(更多坑)**,**反而更难**。
- 作者用 MacBook 多半也是用 Docker/Linux 虚拟机或 Linux CI,不是在 macOS 原生编译。
- **结论:能编得动靠的是"用对发行版/拿现成镜像/认清不需要整个平台",不是换笔记本。这台 Windows+WSL2 完全够用。**

## 4. 教训 & 价值(报告话术)
> 我们曾尝试本机完整复现 world-model 的 9 个 Docker 镜像以端到端运行平台,但该平台为特定 Linux/CI 环境设计,本机从源码构建遭遇一系列版本兼容问题;且复现整个平台并非本任务核心。据此**及时调整方向**,聚焦**算法理解、集成方案设计、核心算法可运行验证**——更贴合 mentor 要求,并产出可演示成果。

**一句话教训:别为"复现别人的基础设施"过度投入,优先抓任务的核心价值(算法与集成)。**
