> 状态:ACTIVE(ROS2 迁移设计输入)。桥接方案(thinbridge TCP:7601)已废弃,本文回答:

## 0. 目标架构

```
world-model(ROS2 jazzy,单一 ROS 图,单一 sim 时钟)
  /wm/cloud3d (PointCloud2, frame=lidar3d_frame, 真3D) ──┐
  /slam/odom  (Odometry, frame=map, child=base_link) ────┤
                                                         ▼
                     GBPlanner-ROS2(voxblox 建图 + RRG 规划,world_frame=map)
                          + 薄触发壳(替 PCI:定时/事件调 gbplanner 服务)
                                                         │
                              /gbp/trajectory (MultiDOFJointTrajectory, frame=map)
                                                         ▼
                     trajectory_to_intent_stage4.py(**不改**,fail-closed 适配器)
                                                         ▼
                     /navlab/fcu/setpoint/intent → fcu_controller → gate
```

一句话:**桥的一切转换要么变成"把 planner 配置成 map 系"这一个参数,要么直接消失。**

### 2.3 薄壳最小保留集(替代 PCI)

丢 PCI,一个 rclcpp/rclpy 薄壳即可,最小契约:

1. **服务 client**:`gbplanner`(planner_msgs/planner_srv)。请求填 `header.frame_id="map"`、`bound_mode` 从 0 起空路径时升到 2、`root_pose` 全零(planner 用当前状态起规划——重规划天然从当前位置续,pci_general 的 reconnectPath 因此可弃)。
2. **发布**:`/gbp/trajectory`(MultiDOFJointTrajectory,**frame_id="map"**,每个 response.path Pose → `transforms[0]`,**QoS 必须 RELIABLE**,见 §3)。
3. **重触发策略**:定时重规划,**周期 ≤25s**。依据:适配器 `TRAJ_MAX_AGE_S=30`(超龄弃轨迹)、跟完后 `TRAJ_STALE_S=15` 宽限;且限速 0.08 m/s 下 30s 只走 2.4m,GBPlanner 单条路径 5~10m 注定走不完就超龄——**周期性从当前位姿重规划是设计,不是 workaround**(阶段2.6 实测 19 条 trajectory 的形态与此一致)。PCI 的"剩余距离/v_max≤0.4s 才重触发"判据基于 v_max=1.0 假设,与适配器 0.08 脱节,弃。
4. **可选保留**:`gbplanner/set_planning_trigger_mode`(kAuto 告知 planner 处于自动探索,影响其内部时间预算记账;不调则默认 kManual,功能不缺失);壳内提供 `planner_control_interface/std_srvs/homing_trigger`(std_srvs/Trigger)服务桩 + `gbplanner/homing` client,接住 rrg 时间预算耗尽的回航请求;不提供则 planner 只报错不崩。
5. **参数**:壳自身只需 `trigger_period`、`world_frame_id(=map)`、输出话题名。planner 侧沿用 `gbplanner_config.yaml` + `voxblox_sim_config.yaml`(world_frame 改 map)+ RobotDynamics 组;`planner_control_interface_sim_config.yaml` 整份可弃(run_mode/robot_type/output_type/init_motion/lead_time 全是 PCI 私货)。
6. **消息包依赖**:planner_msgs 的 srv 里 ROS2 port 最少只要 `planner_srv`(+可选 `planner_homing`、`planner_set_planning_mode`);其余 20 个 srv 随包移植但壳不引用。

## 3. 适配器零改动兼容条件

来源:`integration/ros1_bridge/trajectory_to_intent_stage4.py`(**契约冻结,不改**)。

适配器订阅/发布面:
- 入:`/gbp/trajectory`(MultiDOFJointTrajectory,depth 10 **默认 QoS=RELIABLE**)、`/slam/odom`(sensor_data QoS,位置+map→base_link姿态)、`/gbp/enable`、`/gbp/kill`、`/navlab/fcu/controller/status`、`/navlab/fcu/setpoint/intent`(混流监听)、`/navlab/fcu/local_position_pose`(FCU NED yaw)、`/mavlink_external_nav/status`(ATTITUDE 源年龄)
- 出:`/navlab/fcu/setpoint/intent`、`/navlab/exploration/status`

ROS2 planner 直出 `/gbp/trajectory` 时,零改动需满足:

| 条件 | 依据(适配器行号) | 直连下怎么满足 |
|---|---|---|
| `header.frame_id` **必须严格 == "map"**(否则 blocker `frame_mismatch`) | L189-190 `not in ("map",)` | planner world frame 配成 map 后直出即是 map。**桥时代的 map→world→map 双重改名整条消失,这是直连最干净的一点** |
| 发布 QoS 必须 RELIABLE(适配器订阅用默认 QoS) | L97 | rclcpp/rclpy 默认 QoS 即 RELIABLE,别手滑用 sensor_data 发轨迹 |
| 每点 `transforms[0].translation.{x,y,z}` 被消费;z 作为高度位置目标下发;`rotation`、`time_from_start`、velocities 不消费 | 当前 `on_traj`/`tick` | 壳转换必须保留 3D translation;不得降成 2D 代理 |
| `header.stamp` 不被读取;新鲜度按**收到时刻**的 monotonic 钟算(TRAJ_MAX_AGE 120s / 跟完后 TRAJ_STALE 15s) | 当前 `on_traj`/`blockers` | one-shot 路径覆盖 90s 验收窗,无需周期刷新重置航点 |
| `/slam/odom` frame=map、child=base_link,原生直用 | L96 | 不变,天然满足 |
| `/navlab/fcu/local_position_pose`、`/navlab/fcu/controller/status` 由 fcu_controller 提供 | L100-102 | 不变,与 planner 无关 |
| 空 points 的轨迹被忽略 | L135-136 | planner 空路径时壳干脆不发布(与 PCI 行为一致) |

### body FRD 与坐标语义(点名)

- 当前 fcu_controller 的 intent 契约是机体系 FRD,controller 再按 FCU yaw 旋到 NED。
  adapter 直接使用 `/slam/odom` 的 map→base_link yaw `ψ`:
  `forward=cosψ·vx_map+sinψ·vy_map`,`right=sinψ·vx_map-cosψ·vy_map`。
  第二式的负号来自 ROS base_link 的 y-left 到 FRD y-right,不是经验轴换。
- 第五次 M5 run `20260824T052332.574642383Z` 与第四次 bag 共同证明位置数值关系近似
  `NED=(map_y,map_x)`(det=-1)。旧 `R_align` 强制 det=+1,所以角度随运动方向漂移;
  `THETA_BASE`、短基线更新和 0.35m 冻结均已退出控制链。
- FCU yaw 虽不再参与 adapter 的 map→body 运算,但 downstream 正用它 body→NED;
  因此 yaw 缺失/过期仍必须 fail-closed。
  新鲜度必须由 `/mavlink_external_nav/status.fcu_attitude_age_ms` 证明,不能只看
  会重复携带最后一次 yaw 的 `local_position_pose` 到达时间。
- 但语义上有一处要点名:桥时代"planner 的 world"与"适配器的 map"是**两个名字一套坐标**,靠桥改名维持幻觉;直连后 planner、voxblox、TF、轨迹、odom **全部真名 map,一套坐标一个名字**——排查坐标问题时不再有"这个 world 是谁的 world"的歧义。
- Stage5 早期“intent 不旋转直接作 NED”的结论只适用于旧 controller,已被当前源码
  `world_v=R(yaw_fcu)·v_intent` 与第四次 run MCAP 证伪,不得继续沿用。

## 5. 风险与开放问题

1. **TF 链完整性**(§1-3):直连假设 world-model 原生 `map→odom→base_link` 存在且连续;联调第一件事用 `tf2_echo map lidar3d_frame` 验通,不通再补 odom→TF 广播器。
2. **`base_link→lidar3d_frame` 静态 TF 归属**:确认 world-model 的 robot_state_publisher / gz bridge 是否已发;没有则 ROS2 launch 里补 static_transform_publisher(+0.10m)。
3. **QoS 矩阵**:planner ROS2 port 点云订阅建议 sensor_data(匹配 gz bridge 发布端);`/gbp/trajectory` 发布必须 RELIABLE(§3)。DDS 慢发现教训(B16,28.97s)在同图直连下依旧适用——启动顺序上 planner 后起无妨,但验收探针沿用"type 已发现即等待预算 45s"口径。
4. **voxblox ROS2 化**是移植主工程量(本文只锁契约):world_frame 参数改 map、`use_sim_time=true`、in-process 集成方式(MapManagerVoxblox)保持。
5. **重触发周期与 TRAJ_MAX_AGE 的匹配**(§2.3)是行为正确性的隐形契约,写进壳的默认参数(建议 20s)并在验收断言"无 trajectory_max_age blocker 出现于运动段"。
